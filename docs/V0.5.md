## Product Goal

Create something simple enough for Sola to begin using every day as soon as possible.

V0.5 is a tiny personal daily log dressed like a cozy pixel game: functionally closer to a cute Excel spreadsheet than a generalized wellness platform. It should support daily checkoffs, a few numeric/time fields, food photos, history browsing, and weight progress without becoming a full analytics or habit-management system.

The charm should come primarily from presentation, not feature complexity.

## Scope

V0.5 includes:

- Three primary areas: Today, History, and Progress.
- Authenticated Supabase-backed data shared across phone and computer.
- A small fixed checklist for daily care and wellness tasks.

## Information Architecture

V0.5 has only three active primary areas.

### Today

The main daily check-in and immediate motivation screen. It should feel like a pixel clipboard, daily quest board, notebook page, or small paper sheet inside a cozy pixel environment.

Today has three major pieces:

1. Daily clipboard/check-in.
2. Monthly completion calendar.
3. Current streaks.

On desktop, the daily clipboard should be the left/primary area and the calendar/streaks should be the right/secondary area. On mobile, these pieces can stack vertically. The exact responsive layout can evolve during implementation.

#### Daily Clipboard / Check-In

Today includes a small fixed checklist, initially:

- `morning_skincare` - Morning Skincare.
- `evening_skincare` - Evening Skincare.
- `vitamins` - Vitamins.
- `minoxidil` - Minoxidil.
- `workout` - Worked Out.
- `iron` - Iron.
- `irestore_helmet` - iRestore Helmet.
- `irestore_mask` - iRestore Mask.

Some checklist items are due daily. Some use simple every-other-day recurrence, especially iron and iRestore treatments. If an item is not due on a date, it should not appear as an incomplete task for that date.

Stable machine-readable item keys are historical identifiers. Display labels may change later without changing item keys. There is no user-facing checklist or habit-management UI in V0.5.

Daily checklist items:

- `morning_skincare`
- `evening_skincare`
- `vitamins`
- `minoxidil`
- `workout`

Every-other-day checklist items:

- `iron`
- `irestore_helmet`
- `irestore_mask`

Today also includes basic daily fields:

- Weight.
- Steps.
- Sleep duration.
- Bedtime.
- Wake-up time.
- Approximate calories eaten the previous day.

If Worked out is checked, allow lightweight workout details:

- Activity type.
- Duration.

Today supports uploading one or more food photos for the day with optional lightweight metadata:

- Meal type.
- Short note.

Today's data should be editable throughout the day. Saving a day should update that day's record rather than creating duplicate daily records.

#### Monthly Completion Calendar

Today includes a small visual monthly calendar showing how well Sola completed the due checklist items for each day. It should feel similar in spirit to an activity heatmap, but presented as a cute pixel calendar, wall calendar, tracker sheet, or game-status board rather than a developer dashboard.

Daily completion state is derived from the percentage of checklist items due on that date that were completed:

- Great day: 80-100% of due checklist items completed.
- Good day: 50-79%.
- Some progress: 1-49%.
- No activity: 0%.
- Future date: visually distinct/disabled and not counted as failure.

Only checklist items due on that date count in the denominator. If Iron is every other day and is not due Tuesday, it must not reduce Tuesday's completion percentage.

The calendar should make it satisfying to build up a month of completed days. Exact final colors/art states can change, but behavior should remain separate from visual treatment.

Calendar interaction:

- Today should be visually identifiable.
- Clicking/tapping a past date should open or navigate to that day's History entry if reasonably simple.
- Future dates should not be interactive as completed days.
- Days before V0.5 tracking began should not be treated as failed days.

V0.5 should distinguish these states without overengineering:

- **Tracking expected, no activity:** a date on or after tracking began where due checklist items existed and none were completed.
- **Before tracking began:** a date before the first V0.5 tracked day; show as inactive/neutral rather than failed.
- **Future date:** a date after today; show disabled/unavailable and exclude from completion judgment.

#### Current Streaks

Today includes a small set of motivational streaks derived from data Sola is already entering. Streaks should appear as charming status cards/signs under or near the monthly calendar.

Initial displayed streaks:

- Workout.
- 7+ hours of sleep.
- 7,500+ steps.
- Vitamins.

The initial displayed set should be intentionally small. V0.5 does not need a user-facing streak builder or generalized goal-management system. Targets are simple application configuration/constants.

Approved initial thresholds:

- Sleep goal: 7 or more hours.
- Step goal: 7,500 or more steps.

Checklist streaks count consecutive successful due dates. Daily checklist items are due every calendar day after tracking begins, so their streaks usually count consecutive calendar days. Every-other-day items count consecutive successful due dates, not consecutive calendar days.

Example:

- Iron is due Monday, Wednesday, Friday, and Sunday.
- If all four are completed, Iron has a 4 due-day streak.
- Tuesday, Thursday, and Saturday do not break the streak because Iron was not due.
- A missed scheduled due date breaks that item's streak.

Data-based goal streaks count consecutive calendar days meeting the configured threshold, such as sleep duration of 7+ hours or steps at/above a configured target.

Do not store independent streak counters in V0.5. Derive streaks from canonical daily/checklist data so edits to history naturally update the displayed streaks.

### History

History lets Sola look backward through daily entries. It should feel like a pixel notebook or scrapbook, not a database table.

History includes:

- Browsing previous days.
- Opening a day.
- Viewing that day's checklist, fields, workout details, and food photos.
- Editing a previous day when necessary.
- Food photo gallery.

The food gallery should be a visual grid of clickable photo cards. Each card displays the photo and date, and may show meal type if present. Clicking a card opens a larger view with the image, date, meal type, and note.

### Progress

Progress is a deliberately small dashboard. It should feel like a pixel presentation board, graph-paper panel, or cute chart board rather than a generic dashboard.

Primary progress requirements:

- Starting weight.
- Current/latest weight.
- Total weight change.
- Weight-over-time graph.

Later V0.5 iterations may add simple summaries only if trivial to derive from existing V0.5 records:

- Average steps.
- Number of workouts.
- Average sleep.
- Checklist completion.

Do not expand Progress into a full analytics system.

## Simple Recurrence

V0.5 recurrence is intentionally tiny.

Checklist items can be defined in code or a small static configuration with:

- `key`.
- `label`.
- `cadence`: `daily` or `every_other_day`.
- `anchor_date` for every-other-day items.
- Optional grouping/display metadata.

For every-other-day recurrence, an item is due when the number of days between the selected date and its `anchor_date` is divisible by 2. Dates before the anchor are not due unless deliberately configured otherwise.

Approved every-other-day schedule:

- `iron`
- `irestore_helmet`
- `irestore_mask`

All three every-other-day items use the same anchor date: `2026-08-12`.

Example:

- Iron, iRestore Helmet, and iRestore Mask are due on August 12, August 14, August 16, August 18, and so on.
- They are not due on August 13, August 15, August 17, and so on.

Do not use or rebuild the V1 universal habit scheduling system for V0.5 recurrence.

## Derived Calendar And Streak Data

Calendar completion and streaks should be derived from canonical daily/checklist data wherever practical.

Do not store independent values such as `workout_streak = 6` or permanent daily completion percentages in the initial V0.5 model. These can become inconsistent when historical entries are edited.

Monthly completion derivation:

1. For each date in the displayed month, determine which fixed checklist items were due.
2. Exclude future dates.
3. Treat dates before tracking began as neutral/inactive.
4. Count due items as the denominator.
5. Count completed due items as the numerator.
6. Calculate `completed_due_items / due_items`.
7. Map the percentage to Great, Good, Some progress, or No activity.

If no checklist items were due on a date, display it as neutral rather than failed.

Tracking start:

- V0.5 tracking begins on the date of the user's first saved V0.5 daily entry.
- Dates before the first saved V0.5 daily entry are neutral.
- Pre-tracking dates do not display as failed days, count as 0% completion, break streaks, or reduce completion statistics.
- Future dates are neutral/disabled.
- A saved daily entry with zero completed due checklist items can legitimately represent a 0% / No activity checklist day.

Streak derivation:

1. Pick a streak definition, such as a checklist item or data threshold.
2. Walk backward from today or the selected date.
3. For daily checklist items, inspect each calendar date.
4. For every-other-day checklist items, inspect only dates when the item was due.
5. For data-based streaks, inspect each calendar date and test whether the configured threshold was met.
6. Stop at the first expected date that fails.
7. Return the count of successful expected dates.

This keeps V0.5 motivational without introducing achievements, XP, levels, rewards, badges, challenges, social comparison, leaderboards, or complex gamification infrastructure.

## Proposed V0.5 Data Model

The V0.5 data model names are approved and implemented in `supabase/migrations/0004_v05_daily_tracker.sql`.

Approved tables:

### `v05_daily_entries`

One row per profile and local calendar date.

- `id` uuid primary key.
- `user_id` references `profiles.id`.
- `entry_date` date.
- `weight` numeric nullable.
- `steps` integer nullable.
- `sleep_duration_minutes` integer nullable.
- `bedtime` time nullable.
- `wake_time` time nullable.
- `previous_day_calories` integer nullable.
- `worked_out` boolean not null default false.
- `workout_activity_type` text nullable.
- `workout_duration_minutes` integer nullable.
- `notes` text nullable.
- `created_at` timestamptz.
- `updated_at` timestamptz.
- unique `(user_id, entry_date)`.

This table owns the editable daily scalar fields for V0.5. It also provides source data for data-based streaks and Progress summaries.

### `v05_checklist_completions`

One row per profile, date, and fixed checklist item key.

- `id` uuid primary key.
- `user_id` references `profiles.id`.
- `entry_date` date.
- `item_key` text.
- `completed` boolean not null default false.
- `created_at` timestamptz.
- `updated_at` timestamptz.
- unique `(user_id, entry_date, item_key)`.

The item definitions themselves should remain in code/static config for V0.5, not in a user-facing builder.

Checklist completions are recorded only for fixed item keys. Due-ness is derived from the fixed checklist definitions rather than stored per completion row.

### `v05_food_photos`

One row per uploaded food photo.

- `id` uuid primary key.
- `user_id` references `profiles.id`.
- `entry_date` date.
- `storage_path` text.
- `meal_type` text nullable.
- `note` text nullable.
- `created_at` timestamptz.
- `updated_at` timestamptz.
- `deleted_at` timestamptz nullable.

Food photos should be stored in the approved private Supabase Storage bucket `v05-food-photos`. Storage paths should include an owner/profile prefix so storage policies can enforce access cleanly.

V0.5 should use soft deletion for photo records. Permanent storage deletion is not part of normal V0.5 behavior.

### Derived Views / No Stored Counters

The initial V0.5 schema does not need tables for calendar completion percentages, streak counters, achievements, badges, or goals.

The application should calculate:

- Monthly calendar completion states from checklist definitions plus `v05_checklist_completions`.
- Checklist streaks from due dates plus `v05_checklist_completions`.
- Data-based streaks from configured thresholds plus `v05_daily_entries`.
- Weight progress from `v05_daily_entries.weight`.

Caching or denormalization can be reconsidered later only if performance becomes a real issue.
